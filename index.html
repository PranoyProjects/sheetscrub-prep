Indexing

TypeWhat it doesWhen to use
ClusteredPhysically sorts table rows on disk by the index key — one per tableRange queries, primary key lookups
Non-clusteredSeparate structure pointing back to rows — many per tableFrequent lookups on non-PK columns
CoveringIncludes all columns a query needs, so the engine never touches the base tableHot read-path queries — biggest single perf win

Cardinality matters: index high-cardinality columns (unique-ish values) — indexing a boolean or a 3-value status column rarely helps, since the engine still has to scan most of the table.
Sargability: a predicate is "sargable" if the engine can use an index on it directly. Wrapping an indexed column in a function — WHERE YEAR(order_date) = 2025 — makes it non-sargable; the engine must evaluate the function per row instead. Rewrite as a sargable range: WHERE order_date >= '2025-01-01' AND order_date < '2026-01-01'.
Lakehouse note: Delta Lake / Databricks doesn't use traditional B-tree indexes — instead: Z-ordering co-locates related data on disk (multi-dimensional clustering), data skipping uses file-level min/max statistics to skip whole files, and Bloom filters can be added on specific columns for fast existence checks. Same goal (avoid scanning irrelevant data), different mechanism.

Normalization

FormRuleFixes
1NFAtomic columns — no repeating groups or arrays in a cellUn-atomic values (e.g. "SQL,Python,Spark" in one cell)
2NF1NF + every non-key column depends on the whole primary keyPartial dependency (only applies to composite keys)
3NF2NF + no non-key column depends on another non-key columnTransitive dependency (e.g. storing dept_name in the employees table when it depends on department_id, not employee_id)
4NF3NF + no independent multi-valued dependencies in one tableRare in practice — two unrelated many-valued facts crammed into one table

The three classic anomalies normalization prevents: update (same fact stored in multiple rows, update one and miss the others), insert (can't add a fact until an unrelated fact also exists), delete (deleting one fact accidentally destroys another).
Denormalization is the deliberate reverse — done on purpose in OLAP/analytics for read speed (star schemas, wide Gold tables) at the cost of write-time complexity and some redundancy. This is why an OLTP system (normalized, write-optimized) and a Databricks Gold table (denormalized, read-optimized) look so different even when modeling the same business.

SCD Type 2 (Slowly Changing Dimension)

SCD Type 2 preserves history: instead of overwriting a changed value (Type 1), insert a new row and mark the old one expired. Needs effective_date, expiry_date, and is_current columns.

TypeBehavior
Type 0Fixed — never changes once written
Type 1Overwrite in place — no history kept
Type 2Insert new row + expire old — full audit trail
Type 3Limited history via an extra "previous value" column

Real Type 2 needs two steps in a single Delta MERGE — you can't cleanly expire the old row and insert the new one in one MATCHED clause:

-- Step 1: expire changed rows
MERGE INTO dim_customer AS target
USING staged_updates AS src
ON target.customer_id = src.customer_id AND target.is_current = true
WHEN MATCHED AND target.city != src.city THEN
  UPDATE SET is_current = false, expiry_date = current_date()

-- Step 2: insert new versions for anything that changed
INSERT INTO dim_customer
SELECT src.*, current_date() AS effective_date, NULL AS expiry_date, true AS is_current
FROM staged_updates src
JOIN dim_customer target ON src.customer_id = target.customer_id
WHERE target.is_current = false AND target.expiry_date = current_date();
Try the SCD2 concept in the Sandbox above using SQLite's INSERT ... ON CONFLICT as a simplified stand-in — not identical to Delta's MERGE INTO syntax, but the same expire-then-insert logic.

Query execution order

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
This is the logical order the engine evaluates in — not the order you type it. It's why WHERE can't reference a SELECT alias (WHERE runs before SELECT), but ORDER BY can (it runs after). It's also why HAVING filters on aggregates and WHERE doesn't — WHERE runs before GROUP BY even exists.

Joins, all 6 types + cardinality

JoinReturns
INNEROnly rows with a match on both sides
LEFTAll left rows, matched right columns or NULL
RIGHTAll right rows, matched left columns or NULL
FULL OUTERAll rows from both sides, NULL where unmatched
SELFA table joined to itself (org charts, manager lookups)
CROSSEvery row × every row (Cartesian product, no ON clause)

Join cardinality math — the output row count isn't just "left rows + right rows." For an INNER JOIN, if a key value appears m times on the left and n times on the right, that key alone contributes m × n rows to the output. A table with duplicate keys on both sides of a join is the classic "row count exploded" interview bug — always check for duplicate keys before joining.

Subqueries

TypeRunsExample use
ScalarReturns one valueWHERE salary > (SELECT AVG(salary) FROM employees)
Multi-rowReturns a listWHERE department_id IN (SELECT id FROM active_depts)
Non-correlatedOnce, independent of the outer queryThe two examples above
CorrelatedOnce per outer row — references an outer columnWHERE EXISTS (SELECT 1 FROM t2 WHERE t2.id = t1.id)

A correlated subquery is usually rewritable as a JOIN and often runs faster that way, since the engine can plan it as a single join instead of re-running the subquery per outer row. NOT IN with a subquery that can return NULL is a classic trap — a single NULL in the subquery's result makes the whole NOT IN match nothing. NOT EXISTS doesn't have this problem.

Aggregations — WHERE vs HAVING, COUNT semantics

WHEREHAVING
FiltersIndividual rows, before groupingAggregated groups, after grouping
Can referenceAny columnAggregate functions or GROUP BY columns

COUNT(*) counts all rows including NULLs. COUNT(column) skips NULLs in that column. COUNT(DISTINCT column) counts unique non-NULL values. This distinction is a frequent source of off-by-N bugs when a column has NULLs.

Practice questions (click to reveal answer)

1. Find the 2nd highest salary — two different ways. 
-- Way 1: OFFSET (breaks on ties — skips duplicate top values individually)
SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1;

-- Way 2: DENSE_RANK (ties share a rank, more commonly what's actually wanted)
SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk FROM employees
) t WHERE rnk = 2;
2. Find duplicate rows in a table with no unique ID. 
SELECT first_name, department_id, COUNT(*) AS cnt
FROM employees
GROUP BY first_name, department_id
HAVING COUNT(*) > 1;
3. Remove duplicates, keeping one copy (no ctid/rowid available, e.g. in Databricks). 
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY first_name, department_id ORDER BY employee_id) AS rn
  FROM employees
)
SELECT * FROM ranked WHERE rn = 1;
4. Employees earning more than their manager (self-join). 
SELECT e.first_name AS employee, e.salary, m.first_name AS manager, m.salary AS mgr_salary
FROM employees e
JOIN employees m ON e.manager_id = m.employee_id
WHERE e.salary > m.salary;
5. Running total and 3-row moving average. 
SELECT txn_date, amount,
  SUM(amount) OVER (ORDER BY txn_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
  AVG(amount) OVER (ORDER BY txn_date ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS moving_avg_3
FROM transactions
ORDER BY txn_date;
6. Gaps-and-islands: find consecutive date streaks per employee. 
-- The trick: (date - ROW_NUMBER) is constant within a consecutive streak
WITH numbered AS (
  SELECT employee_id, visit_date,
    ROW_NUMBER() OVER (PARTITION BY employee_id ORDER BY visit_date) AS rn
  FROM visits
),
grouped AS (
  SELECT *, DATE(visit_date, '-' || rn || ' days') AS grp
  FROM numbered
)
SELECT employee_id, MIN(visit_date) AS streak_start, MAX(visit_date) AS streak_end, COUNT(*) AS streak_len
FROM grouped
GROUP BY employee_id, grp;
7. Top-N per group (e.g. top 2 highest-paid per department). 
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rn
  FROM employees
)
SELECT * FROM ranked WHERE rn <= 2;
8. Find orphaned foreign keys (data quality check). 
SELECT e.* FROM employees e
LEFT JOIN departments d ON e.department_id = d.department_id
WHERE d.department_id IS NULL;
9. PIVOT-style transform without a native PIVOT (conditional aggregation). 
SELECT department_id,
  SUM(CASE WHEN job_title = 'Engineer' THEN 1 ELSE 0 END) AS engineers,
  SUM(CASE WHEN job_title = 'Manager' THEN 1 ELSE 0 END) AS managers
FROM employees
GROUP BY department_id;
10. Rewrite a correlated subquery as a JOIN. 
-- Correlated subquery:
SELECT * FROM departments d
WHERE EXISTS (SELECT 1 FROM employees e WHERE e.department_id = d.department_id);

-- As a JOIN (usually faster):
SELECT DISTINCT d.* FROM departments d
JOIN employees e ON e.department_id = d.department_id;
11. Alternate odd/even rows using ROW_NUMBER + MOD. 
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (ORDER BY employee_id) AS rn FROM employees
) t WHERE rn % 2 = 0;  -- even rows only; use = 1 for odd
12. Create an empty table with the same structure as another (no data). 
SELECT * INTO employees_backup FROM employees WHERE 1 = 0;
-- SQLite/Spark SQL equivalent (CTAS with an always-false filter):
CREATE TABLE employees_backup AS SELECT * FROM employees WHERE 1 = 0;
13. Find employees hired in the last 6 months. 
SELECT * FROM employees
WHERE hire_date >= DATE('now', '-6 months');
14. Find gaps in a numeric sequence (e.g. missing invoice numbers). 
WITH RECURSIVE seq(n) AS (
  SELECT MIN(invoice_id) FROM invoices
  UNION ALL
  SELECT n+1 FROM seq WHERE n < (SELECT MAX(invoice_id) FROM invoices)
)
SELECT n AS missing_invoice_id FROM seq
WHERE n NOT IN (SELECT invoice_id FROM invoices);
15. Sequentially available seats problem (find a run of N consecutive free seats). 
-- Same gaps-and-islands trick as the streak problem: (seat_number - ROW_NUMBER) is
-- constant within a consecutive run of free seats.
WITH free_seats AS (
  SELECT seat_number, ROW_NUMBER() OVER (ORDER BY seat_number) AS rn
  FROM seats WHERE status = 'free'
),
runs AS (
  SELECT *, seat_number - rn AS grp FROM free_seats
)
SELECT MIN(seat_number) AS run_start, COUNT(*) AS run_length
FROM runs GROUP BY grp HAVING COUNT(*) >= 3;  -- 3+ consecutive free seats
16. UNPIVOT-style transform: turn columns into rows. 
-- If you have q1_sales, q2_sales, q3_sales, q4_sales columns per employee:
SELECT employee_id, 'q1' AS quarter, q1_sales AS sales FROM sales_wide
UNION ALL SELECT employee_id, 'q2', q2_sales FROM sales_wide
UNION ALL SELECT employee_id, 'q3', q3_sales FROM sales_wide
UNION ALL SELECT employee_id, 'q4', q4_sales FROM sales_wide;
17. Recursive CTE: build an org chart showing each employee's full management chain. 
WITH RECURSIVE org_chart AS (
  SELECT employee_id, first_name, manager_id, 0 AS depth, first_name AS chain
  FROM employees WHERE manager_id IS NULL  -- top of the org
  UNION ALL
  SELECT e.employee_id, e.first_name, e.manager_id, oc.depth + 1, oc.chain || ' > ' || e.first_name
  FROM employees e
  JOIN org_chart oc ON e.manager_id = oc.employee_id
)
SELECT * FROM org_chart ORDER BY depth;

Note: real-world SQL engines vary on recursive CTE syntax (Databricks/Spark SQL support differs from SQLite) — always check the target engine's exact recursive-CTE dialect before relying on this pattern in production.

18. Filter rows without using a WHERE clause. 
SELECT department_id, COUNT(*) AS cnt
FROM employees
GROUP BY department_id
HAVING COUNT(*) > 5;  -- HAVING can filter without any WHERE clause present
19. Highlight/find records where a countDistinct join-back reveals a data conflict (e.g. an employee_id mapped to more than one department across source tables). 
SELECT employee_id, COUNT(DISTINCT department_id) AS dept_count
FROM employees_source_union   -- e.g. a UNION of multiple source feeds
GROUP BY employee_id
HAVING COUNT(DISTINCT department_id) > 1;
20. QUALIFY — filter on a window function without wrapping the query in a subquery (Databricks/Snowflake support this; SQLite doesn't). 
-- Databricks SQL / Snowflake:
SELECT *, ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rn
FROM employees
QUALIFY rn = 1;

-- The portable equivalent everywhere else (including this app's SQLite engine):
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rn
  FROM employees
) t WHERE rn = 1;

Architecture & execution flow

Driver — runs your code, builds the DAG, dispatches tasks. Lives outside the cluster's worker nodes.
Executors — run on worker nodes, execute tasks, cache data, return results to the driver.
Cluster manager — allocates resources (YARN, Kubernetes, Standalone, Mesos).
Flow: code → logical plan → Catalyst optimizer (predicate pushdown, column pruning) → physical plan → DAG scheduler splits into stages at shuffle boundaries → task scheduler → executors → results back to driver.

TransformationAction
LazinessBuilds the plan, doesn't run yetTriggers actual execution
Examplesfilter, select, withColumn, groupByshow, count, collect, write

Narrow transformation: each output partition depends on one input partition (filter, select — no shuffle).
Wide transformation: output depends on multiple input partitions (groupBy, join — requires a shuffle, a stage boundary).

Optimization cheat sheet

TechniqueSolvesHow

Predicate pushdownLate filteringPush WHERE down to the file-read layer
Broadcast joinSlow joins w/ small tableCopy small table to all workers, avoid shuffle
Z-Ordering (Delta)Slow lookups on non-partition colsCo-locate related data on disk

cache()/persist()Recomputing same DataFrameKeep result in memory/disk after first compute
repartition vs coalesceWrong file count/skewrepartition = full shuffle rebalance; coalesce = merge, no shuffle

Diagnose from the Spark UI first (shuffle/skew? small files? unnecessary scan?), then match the fix to the actual bottleneck — don't apply the list blind.

The "big three," as actual code — these three show up in almost every 2026 interview report regardless of company:

from pyspark.sql import functions as F

# 1. AQE — on by default in modern Spark, but explicit is safer to state in an interview
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")

# 2. Broadcast join — force it explicitly when you know one side is small (<~10MB)
result = big_orders_df.join(F.broadcast(small_country_lookup_df), on="country_code")

# 3. Partition fact tables by the most-filtered column, not an arbitrary one
(
    orders_df.write
    .format("delta")
    .partitionBy("order_date")   # e.g. if 90% of queries filter WHERE order_date = ...
    .mode("overwrite")
    .saveAsTable("gold.orders")
)

Batch vs streaming, exactly-once, and watermarking — code, not just definitions:

# Watermarking: tells Spark how late a "late-arriving" event can be before it's dropped,
# which bounds how much state Structured Streaming has to keep around for aggregations.
windowed_counts = (
    events_df
    .withWatermark("event_time", "10 minutes")   # tolerate up to 10 min of lateness
    .groupBy(F.window("event_time", "5 minutes"), "device_id")
    .count()
)

# Exactly-once semantics: achieved via checkpointing + idempotent sinks, NOT a magic flag.
# The checkpoint tracks exactly which offsets have been processed, so a restart resumes
# from the correct point instead of re-processing or skipping data.
query = (
    windowed_counts.writeStream
    .format("delta")
    .option("checkpointLocation", "/mnt/checkpoints/device_counts")  # this IS the exactly-once mechanism
    .outputMode("update")
    .trigger(processingTime="1 minute")
    .table("silver.device_counts")
)

Common interview follow-up: "what happens without a watermark on a streaming aggregation?" — the answer is unbounded state growth, since Spark has no way to know an aggregation window is "done" and can be dropped from memory.

1. Read a CSV with an explicit schema (not inferSchema). 
from pyspark.sql.types import StructType, StructField, IntegerType, StringType, DoubleType

schema = StructType([
    StructField("employee_id", IntegerType(), True),
    StructField("first_name", StringType(), True),
    StructField("salary", DoubleType(), True),
])
df = spark.read.csv("employees.csv", header=True, schema=schema)

Why: inferSchema does a full extra pass over the data and one bad row can silently downgrade a whole column's type (e.g. an INT column becomes STRING). Explicit schema avoids both problems.

2. Top-N per group using Window (equivalent to the SQL ROW_NUMBER pattern).

from pyspark.sql import functions as F

w = Window.partitionBy("department_id").orderBy(F.desc("salary"))
result = (
    df.withColumn("rn", F.row_number().over(w))
      .filter(F.col("rn") <= 2)
)

9. Diagnose driver vs executor OOM — what's different about each?

Driver OOM — usually caused by .collect() pulling too much data back to the driver, or too many small tasks/broadcast variables accumulating there. Fix: avoid collect() on large data, increase driver memory, or write results directly instead of collecting.
Executor OOM — usually a skewed partition, a huge broadcast join, or too many cached DataFrames competing for executor memory. Fix: repartition to even out skew, avoid broadcasting a table that's actually large, unpersist cached data you no longer need.

10. .transform() vs a UDF — when to use which?

.transform() chains a plain Python function that takes and returns a DataFrame — it's just for readable method chaining, still uses native Spark operations, still gets Catalyst-optimized. A UDF wraps row-level Python logic that Spark can't express natively — it's a performance cliff, since Catalyst can't see inside it and each row round-trips through Python (or worse, JVM↔Python serialization via py4j). Prefer built-in pyspark.sql.functions or .transform() whenever possible; reach for a UDF only when there's truly no native equivalent.

11. Do an SCD Type 2 upsert with Delta MERGE — the full 2-step pattern in PySpark. 
from delta.tables import DeltaTable

target = DeltaTable.forName(spark, "dim_customer")

# Step 1: expire rows whose tracked columns changed
target.alias("t").merge(
    updates_df.alias("s"), "t.customer_id = s.customer_id AND t.is_current = true"
).whenMatchedUpdate(
    condition="t.city != s.city",
    set={"is_current": "false", "expiry_date": "current_date()"}
).execute()

# Step 2: insert new versions for changed rows
new_versions = (
    updates_df.alias("s")
    .join(target.toDF().alias("t"), "customer_id")
    .where("t.is_current = false AND t.expiry_date = current_date()")
    .select("s.*")
    .withColumn("effective_date", F.current_date())
    .withColumn("expiry_date", F.lit(None))
    .withColumn("is_current", F.lit(True))
)
new_versions.write.format("delta").mode("append").saveAsTable("dim_customer")
12. Cache vs persist — what's actually different, and when would you NOT cache?

.cache() is shorthand for .persist(StorageLevel.MEMORY_AND_DISK). Use persist directly when you want a different storage level (e.g. MEMORY_ONLY for speed if it fits, or DISK_ONLY if memory is tight). Don't cache a DataFrame you only use once — caching costs the first computation plus storage overhead, and only pays off if you reuse the same DataFrame multiple times. Also remember to .unpersist() when done, or it holds memory for the rest of the session.

16. Two DataFrames should have identical row counts after a transformation, but they don't. How do you debug which rows got lost or duplicated? 
# Rows that exist in original but vanished after transform:
lost = original_df.join(transformed_df, "id", "left_anti")

# Rows that got duplicated (appear more than once in the result):
from pyspark.sql import functions as F
dupes = transformed_df.groupBy("id").count().filter(F.col("count") > 1)

19. What does AQE (Adaptive Query Execution) actually change at runtime, concretely?

Three main things: 1) dynamically coalesces post-shuffle partitions that turned out too small, 2) switches a sort-merge join to a broadcast join if runtime stats show one side is actually small, 3) splits skewed partitions detected after the shuffle actually happens (not guessable beforehand). It works by inserting query-plan re-optimization points at shuffle boundaries, using real data statistics gathered from the previous stage rather than the optimizer's upfront estimates.

def merge_sorted(a, b):
    i = j = 0
    out = []
    while i < len(a) and j < len(b):
        if a[i] <= b[j]:
            out.append(a[i]); i += 1
        else:
            out.append(b[j]); j += 1
    out.extend(a[i:])
    out.extend(b[j:])
    return out

4. Binary tree traversal — inorder, without recursion (using a stack). 
class Node:
    def __init__(self, val, left=None, right=None):
        self.val, self.left, self.right = val, left, right

def inorder_iterative(root):
    stack, result, node = [], [], root
    while stack or node:
        while node:
            stack.append(node)
            node = node.left
        node = stack.pop()
        result.append(node.val)
        node = node.right
    return result

tree = Node(2, Node(1), Node(3))
print(inorder_iterative(tree))  # [1, 2, 3]
5. Find the median of a large list without loading it all into a single sort (streaming-friendly approach using heaps). 
import heapq

class MedianFinder:
    def __init__(self):
        self.lo = []  # max-heap (inverted), holds smaller half
        self.hi = []  # min-heap, holds larger half
    def add(self, num):
        heapq.heappush(self.lo, -num)
        heapq.heappush(self.hi, -heapq.heappop(self.lo))
        if len(self.hi) > len(self.lo):
            heapq.heappush(self.lo, -heapq.heappop(self.hi))
    def median(self):
        if len(self.lo) > len(self.hi):
            return -self.lo[0]
        return (-self.lo[0] + self.hi[0]) / 2

mf = MedianFinder()
for n in [5, 15, 1, 3]: mf.add(n)
print(mf.median())  # 4.0

12. Implement a basic hash function and explain what "resizing" means for a hash table. 
def simple_hash(key, table_size):
    return sum(ord(c) for c in str(key)) % table_size

print(simple_hash("employee_42", 16))

Resizing: when a hash table gets too full (load factor exceeds a threshold, often ~0.7), it allocates a larger backing array and re-hashes every existing key into new bucket positions — because the bucket index depends on hash(key) % table_size, and table_size just changed. This is why hash table inserts are usually O(1) but occasionally O(n) during a resize.

Learn: Salesforce Data Cloud

Data Cloud is SaaS-only — there's no in-browser way to execute it. This is reference material: the object model and how each concept maps to what you already know from SQL/PySpark/Databricks.

Core object model

Data Cloud conceptWhat it isClosest equivalent
Data StreamIngests data from a source (Salesforce CRM, S3, ingestion API) into Data CloudDatabricks Auto Loader / COPY INTO
Data Lake Object (DLO)Raw ingested data, schema mostly as-is from sourceBronze layer / raw table
Data Model Object (DMO)Mapped to Data Cloud's canonical schema so different sources can be joinedSilver/conformed layer, dimensional model
Calculated InsightA metric computed across DMOs on a schedule (SQL-like definition)SQL aggregation / Databricks Gold table
Identity ResolutionRule-based matching to merge records into one Unified IndividualFuzzy join / dedup logic
SegmentA filtered audience built from DMOs/Calculated InsightsWHERE clause / filtered view
Activation TargetWhere a Segment gets pushed (Marketing Cloud, ad platform, webhook)ETL "Output" node / API push

End-to-end flow

1. Data Stream pulls data in (from Salesforce, cloud storage, or an ingestion API) → lands as a DLO.
2. DLOs are mapped to DMOs against Data Cloud's canonical schema, so a "Contact" from Salesforce and a "Customer" from an e-commerce system land in the same shape.
3. Identity Resolution rules merge DMO records that represent the same real person into a Unified Individual.
4. Calculated Insights compute metrics (lifetime value, engagement score) across the unified data — this is the closest thing to writing SQL in Data Cloud, it uses a similar declarative syntax.
5. A Segment filters the unified population down to a target audience.
6. An Activation Target sends that segment somewhere it can be used (an ad platform, Marketing Cloud, a webhook to your own system).

Identity Resolution, deeper

An Identity Resolution ruleset has two parts: match rules (which fields make two records "the same person" — exact email match, or fuzzy name+phone) and reconciliation rules (when two matched records disagree on a field, which source wins — most recent, a priority order, most complete).
Matches form a graph, not just pairs — if A matches B and B matches C, all three merge into one Unified Individual even if A and C never matched directly. This is the same transitive-closure problem as connected-components in graph theory.
Runs in batch, not real-time — a new record isn't merged into its Unified Individual until the next Identity Resolution run completes.

Data Cloud's Calculated Insight builder is visual, but underneath it's expressing something SQL-shaped. Example — "average order value per customer, last 90 days":

Practice questions (click to reveal answer)

1. A customer exists in both Salesforce CRM and an e-commerce platform with slightly different names. How does Data Cloud know they're the same person?

Identity Resolution match rules — e.g. fuzzy match on (normalized name + phone) or exact match on email — merge both source DMO records into one Unified Individual. The two original records still exist as-is; the merge creates a link, it doesn't overwrite either source.

2. Two matched records disagree on "city" — Salesforce says Austin, the e-commerce system says Dallas. What decides the final value?

A reconciliation rule — commonly "most recently updated source wins," but it can also be a fixed source-priority order (e.g. always trust CRM over e-commerce) or "most complete record wins." This is configured per field, not globally.

3. Marketing wants "customers who spent over $500 in the last 90 days AND haven't opened an email in 30 days" pushed to an ad platform. Name the 3 Data Cloud objects involved, in order.

1) A Calculated Insight computing 90-day spend per customer. 2) A Segment filtering on that Calculated Insight + an engagement DMO field for email opens. 3) An Activation Target pointing at the ad platform, which the Segment gets pushed to.

4. Why can't you just query Data Cloud data live from an external BI tool the way you'd query a database?

You actually can — via the Data Cloud Query API or Data Federation, which reads live without copying data out. The distinction from a normal database: Data Cloud isn't primarily built for ad-hoc arbitrary SQL; its core workflows (Calculated Insights, Segments) are scheduled/batch, and federation is the escape hatch for real-time external querying.

5. A new order lands via the Ingestion API. How long until it's reflected in a customer's Unified Individual profile?

Not immediately — the raw record lands as a DLO right away, but it isn't merged into the Unified Individual until the next scheduled Identity Resolution run completes. This batch-not-realtime behavior is a common gotcha when someone expects Data Cloud to behave like a live transactional system.

6. What's the difference between a Data Lake Object and a Data Model Object, and why does Data Cloud need both?

A DLO holds raw ingested data close to its source shape — a Salesforce Contact DLO and a Shopify Customer DLO look nothing alike. A DMO maps both into Data Cloud's canonical schema (e.g. both become "Individual" records with the same field names), which is what makes cross-source joining, Identity Resolution, and Calculated Insights possible at all. Without the DMO layer, every source would need custom one-off logic to combine with every other source.

7. A Segment built last week now returns zero members. What would you check?

1) Did the underlying Calculated Insight or DMO it filters on stop refreshing (check its last-run status)? 2) Did an upstream Data Stream fail or pause? 3) Did the filter reference a field that got renamed/removed in a DMO update? 4) Is the Segment's publish schedule itself paused? Segments don't error loudly when their inputs go stale — they just quietly return fewer or zero members.

8. What's a Data Kit, and when would you use one instead of building from scratch?

A pre-built template (often partner-published) bundling DMOs, mappings, and sometimes Calculated Insights for a common use case (e.g. a specific industry's standard customer 360 model). Use one to stand up a proven structure fast instead of designing the object model from zero — then customize from there rather than starting blank.

9. Explain the difference between a Calculated Insight and a regular DMO field, with an example.

A DMO field is a direct, stored attribute from a source (e.g. Order.TotalAmount). A Calculated Insight is a computed metric, evaluated on a schedule, often aggregating across many rows (e.g. "average order value over the last 90 days" — this doesn't exist as a single field anywhere, it's derived). Calculated Insights are Data Cloud's closest equivalent to a SQL aggregation query, and they're what most Segments actually filter on.

10. Two source systems disagree on a customer's email — one has an old address, one has a new one, and neither timestamp is reliable. How do you handle it?

Without a trustworthy recency signal, fall back to a source-priority reconciliation rule instead of "most recent" — designate one system as the authoritative source for that field (e.g. always trust the CRM over a marketing tool for email). This is a common real-world case where "most recent" isn't actually available or trustworthy, so the ruleset needs an explicit fallback.

11. Why might the same physical person end up as two separate Unified Individuals?

Match rules didn't find enough overlap — e.g. they used a work email in one system and a personal email in another, with no phone/name match strong enough to link them. This is the mirror image of over-merging: too-loose rules wrongly combine different people, too-strict rules wrongly keep the same person split. Tuning match rules is a real precision/recall tradeoff, not a one-time setup.

12. Your company wants to activate a Segment to a channel Data Cloud doesn't have a native Activation Target for. What's the workaround?

Use the Ingestion/Query API pattern in reverse — export the Segment's membership via the Data Cloud Query API, then push it to the target channel yourself via that channel's own API (a custom integration). Native Activation Targets cover the common cases; anything outside that list needs this manual bridge.

Salesforce Admin — practice questions (click to reveal answer)

1. A user says they can't see a field on a record, even though their Profile has Edit access to that field. What else could be blocking it?

Field-Level Security exists at both the Profile AND any assigned Permission Sets — but also check the Page Layout assigned to that user's Profile+Record Type combo (a field can have FLS access but simply not be placed on the layout they're viewing), and whether it's a Lightning Record Page component visibility rule hiding it conditionally.

2. OWD for Opportunities is Private. A rep can't see their teammate's opportunity even though they're in the same role. Why might the role hierarchy not be helping here?

Role hierarchy grants visibility upward (a manager sees subordinates), not sideways between peers at the same level. Two reps in the same role don't automatically see each other's records — that needs an explicit sharing rule (e.g. a criteria-based or ownership-based sharing rule for that role/group) or a manual share.

3. When would you use a Validation Rule instead of a Flow to enforce a business rule?

Validation Rules are simpler, run synchronously at save time, and are the right tool for hard "block the save" logic (e.g. "Close Date can't be in the past"). Flow is better when the logic needs to do something beyond blocking — update other records, send notifications, or run multi-step logic. Reaching for Flow when a Validation Rule would do is unnecessary complexity.

4. What's the actual difference between a Permission Set and a Permission Set Group?

A Permission Set Group bundles multiple Permission Sets into one assignable unit — instead of assigning 5 separate Permission Sets to every new hire on a team, you assign one Permission Set Group. It also supports "muting" specific permissions from within the bundled sets, which individual Permission Sets can't do to each other.

5. A picklist field needs different values depending on whether the record is "Enterprise" or "SMB." How do you set that up?

Record Types + picklist value sets. Create two Record Types (Enterprise, SMB), then restrict which picklist values are available per Record Type on that field. Each Record Type can also have its own Page Layout, so the two processes can look and behave differently on the same object.

6. What happens to existing data if you change a field's data type, e.g. Text to Picklist?

Salesforce attempts to convert existing values automatically where it can (exact text matches become picklist values); anything that doesn't cleanly map may become blank or require manual review — this is a real risk in production, always test in a sandbox first and check the conversion preview Salesforce shows before confirming.

7. Explain the difference between a Public Group, a Queue, and a Role for sharing purposes.

Role — hierarchical, tied to org structure, grants upward visibility. Public Group — flat, arbitrary collection of users/roles/other groups, used as a sharing-rule target with no hierarchy implied. Queue — an object-specific holding area for unassigned records (e.g. unassigned Cases/Leads) that a group of users can pull from — it's about record ownership/routing, not just visibility.

8. A sandbox refresh just happened and several integrations broke. What's the most likely cause?

Sandbox refreshes typically reset/regenerate API keys, Named Credentials, and Connected App settings, and can overwrite sandbox-specific configuration with production values. Integration user credentials, OAuth tokens, and any sandbox-only endpoint overrides usually need to be reconfigured post-refresh — this is expected, not a bug.

9. What's the actual execution order when a record is saved (validation rules, triggers, workflow, etc.)?

Simplified: system validation (required fields, data types) → before-save Flows/triggers → custom Validation Rules → duplicate rules → save to database (assigns ID) → after-save triggers/Flows → assignment/auto-response rules → workflow rules and their immediate actions → escalation rules → entitlement rules → roll-up summary field recalculation on parent. Getting this wrong is a classic source of "why did the automation run twice" or "why didn't my validation catch this" bugs.

Partitioning vs Bucketing vs Z-Order

TechniqueWhat it doesBest for
PartitioningPhysical folders by a low/medium-cardinality column (e.g. date)Columns frequently filtered on, with manageable distinct-value count
BucketingFixed hash-based file count, regardless of value cardinalityHigh-cardinality join/aggregation keys — avoids the tiny-partition problem
Z-OrderingMulti-dimensional co-location within files (Delta-specific)Filtering on multiple non-partition columns at once

Common mistake: partitioning on a high-cardinality column (like a raw user ID) creates the "small file problem" — thousands of tiny partitions, each with a handful of rows, which kills read performance. That's exactly when bucketing or Z-order is the better fit.

Capacity planning math

partitions ≈ data size / 128MB (target partition size)
parallel task capacity = worker nodes × cores per node
execution waves = partitions / parallel task capacity
usable memory per executor ≈ (RAM per node × ~70%) / executors per node

Worked example: 2GB of data, targeting 128MB partitions → ~16 partitions. A cluster with 4 worker nodes × 4 cores = 16 parallel task slots → all 16 partitions run in a single wave. Double the data with the same cluster → 2 waves, roughly double the wall-clock time for that stage.

Streaming & workflows

Structured Streaming — micro-batch (or continuous) processing on the same DataFrame API as batch; checkpoints track progress so a restart resumes exactly where it left off, not from scratch.
Auto Loader — incrementally and efficiently discovers new files landing in cloud storage, without listing the whole directory each run.
DLT (Delta Live Tables) — declarative pipeline framework; define the target tables and their dependencies, DLT handles orchestration, and expectations (data quality rules) can warn, drop, or fail the pipeline per severity.
Workflows — Databricks' job scheduler/orchestrator; tasks can pass values to each other and run on a schedule or trigger.
DABs (Databricks Asset Bundles) — infrastructure-as-code for CI/CD of notebooks, jobs, and pipelines across dev/staging/prod.

Row filter — a SQL function that returns a boolean, applied automatically to every query against the table:

CREATE FUNCTION region_filter(region STRING)
RETURN IF(IS_ACCOUNT_GROUP_MEMBER('admins'), true, region = current_user_region());

ALTER TABLE sales.orders SET ROW FILTER region_filter ON (region);
-- A non-admin querying sales.orders now only ever sees rows matching their own region,
-- with no change needed to their query — the filter is invisible and non-bypassable.

Column mask — a SQL function applied to a specific column's returned value:

CREATE FUNCTION mask_ssn(ssn STRING)
RETURN CASE WHEN IS_ACCOUNT_GROUP_MEMBER('hr_admins') THEN ssn
            ELSE CONCAT('***-**-', RIGHT(ssn, 4)) END;

ALTER TABLE employees.records ALTER COLUMN ssn SET MASK mask_ssn;
-- hr_admins see the real SSN; everyone else sees ***-**-1234

Lineage — queryable directly via Unity Catalog's system tables, not just the UI graph:

SELECT source_table_full_name, target_table_full_name, source_type
FROM system.access.table_lineage
WHERE target_table_full_name = 'main.gold.revenue_summary'
ORDER BY event_time DESC;

Audit logging — also a system table, queryable with plain SQL like anything else:

SELECT user_identity.email, action_name, request_params, event_time
FROM system.access.audit
WHERE action_name = 'deleteTable'
  AND event_time >= current_date() - INTERVAL 7 DAYS
ORDER BY event_time DESC;
-- "who deleted what, when" — this is exactly the query an interviewer expects
-- when asking how you'd investigate an incident after the fact.

Grant access — this is what "account-level, not per-workspace" means in practice: one GRANT, enforced everywhere the object is reachable:

GRANT SELECT ON TABLE main.gold.revenue_summary TO `analytics_team`;
GRANT USE CATALOG ON CATALOG main TO `analytics_team`;
-- Unlike per-workspace ACLs, this one grant is enforced identically regardless
-- of which workspace, cluster, or SQL warehouse someone queries it from.

Practice questions (click to reveal answer)

1. A Gold dashboard number suddenly looks wrong. Walk through your diagnosis, in order.

1) Check DESCRIBE HISTORY on the Gold table — was there an unexpected write/overwrite? 2) Trace lineage backward through Silver to Bronze — did an upstream schema change silently drop or nullify a column? 3) Check the job run history — did the pipeline actually run, or fail silently and serve stale data? 4) If Gold is a MERGE-based incremental table, check for a non-idempotent write (re-running the same batch twice without dedup logic would double-count).

2. Someone accidentally dropped a managed table. Can you get it back?

If it's Delta and within the VACUUM retention window (default 7 days), the data files still exist — you can restore via RESTORE TABLE t TO VERSION AS OF n if the metadata/history is intact, or by recreating the table pointing at the old data path if the catalog entry itself was dropped. This is exactly why VACUUM's retention period is a real tradeoff, not just disk-space hygiene — shortening it trades safety for storage cost.

3. Two jobs both MERGE into the same Delta table at the same time and one fails with a concurrency exception. Why, and how do you avoid it?

Delta uses optimistic concurrency control — both writers assume no conflict, and if their target row ranges actually overlap, the loser fails at commit time rather than silently corrupting data. Fix: don't run overlapping MERGE jobs against the same table concurrently; serialize them, or partition the work so each job's write range genuinely can't overlap the other's.

4. Your Databricks bill doubled this month with no obvious usage increase. What do you check?

Common culprits: a job stuck in an all-purpose (interactive) cluster instead of a cheaper job cluster; auto-scaling misconfigured so clusters over-provision; a cluster left running idle (no auto-termination set); a query regression causing full-table scans where partition pruning used to apply; or a new streaming job with checkpoints creating cluster churn.

5. Design an end-to-end pipeline: raw JSON events land in cloud storage every few minutes, need to reach a queryable Gold table with data quality checks.

Auto Loader ingests new files incrementally into Bronze (raw, as-is). A DLT pipeline (or scheduled job) cleans/conforms into Silver, with expectations to warn/drop/fail on bad records (e.g. malformed JSON, missing required fields) at a chosen severity. A final aggregation step produces Gold. Orchestrate the whole thing as a Databricks Workflow with task dependencies, scheduled or triggered by new-file arrival.

6. What's the difference between schema enforcement failing and schema evolution succeeding — same underlying mismatch, different outcome. Why?

By default, Delta rejects a write whose schema doesn't match the target table (enforcement) — this protects existing consumers from a surprise structural change. If you explicitly opt in with mergeSchema (add new columns) or overwriteSchema (replace schema entirely) as write options, the same mismatch is allowed through instead. It's the same mechanism, gated by an explicit flag — never silent by default.
